# CareConnect CI security

The dispatcher belongs to the separate `h4timfr/care-connect-ci` repository. Keep this repository disconnected from Vercel and all deployment integrations. The workflow runs manually on protected `main` with a read-only GitHub token. It accepts no inputs. Its application repository, candidate commit, test-patch commit, and supervisor baseline are fixed in reviewable CI files. Actions and the Supabase CLI use fixed pins.

Require pull requests and code-owner approval for changes to `main`. Require explicit review from `@h4timfr`, dismiss stale approvals, restrict direct pushes and bypass permissions, and prohibit force pushes and deletion. Have a separate authorized contributor open PRs that need the owner's approval. Review changes to the workflow, dispatcher, vendored supervisor and phase helpers, SHA-256 manifest, candidate allowlist, and CODEOWNERS. The workflow checks GitHub's protected-ref flag at runtime. Before enabling dispatch, verify the actual policy and that the repository's visibility and plan support enforcement.

The application fetch writes only Git objects to a bare, run-owned store. It uses anonymous HTTPS when the source permits that. If the application repository is private, provide a separately approved `CARECONNECT_APP_CONTENTS_READ` secret restricted to read-only contents of `h4timfr/care-connect-chennai`. Restrict CI repository write access to trusted maintainers. The fetch step supplies the optional credential through the Git process environment, limits it to the fixed HTTPS URL, disables redirects, and exits before workspace preparation. The isolated test phase uses a local bundle with network protocols disabled. Neither workflow needs staging credentials, production credentials, or a Supabase access token.

The five vendored supervisor files match the approved Git blobs byte-for-byte. The SHA-256 manifest also pins the supporting scripts, lockfile, and migration inventory. The standalone supervisor runs from this repository. The bootstrap extracts only approved support and SQL paths. The test phase verifies the root-owned receipt and imports the exact application object after egress is removed. It extracts only named app and fixture paths and leaves candidate workflows inert.
